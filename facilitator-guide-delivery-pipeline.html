“Where does a change spend most of its time waiting?”

A delivery pipeline is the automated path a change takes from a developer's commit to running in front of users: build, test, check, deploy, release and monitor. Continuous integration (CI) means everyone merges small changes to the main branch often, and every merge is built and tested automatically. Continuous delivery (CD) means every change that passes is ready to release at any time. The canvas makes the pipeline visible to the whole team, including people who don't work on it every day, so you can see where time goes and choose one improvement. The ideas come from Jez Humble and David Farley's Continuous Delivery.

1Before the session

  • Print the board at A3 or 11×17, or load the SVG as a digital background
  • Ask someone who knows the pipeline to sketch its real stages; rename the board's stages to match
  • Pull rough numbers if you can: how long each stage takes, how often it fails, how many deploys a week
  • Invite testers, operations and security people as well as developers
  • Non-engineers are welcome: the map is meant to be understood by everyone

3What to look for

Most of the time a change takes is usually waiting, not working.

Waits

  • Queues for review or approval
  • Shared environments
  • Batching changes up

Failures

  • Flaky tests
  • Broken builds left red
  • Environment differences

Manual steps

  • Hand-run scripts
  • Tickets to other teams
  • Copy-paste config

Gates

  • Which ones catch real problems?
  • Which could be automated?

Feedback speed

  • Minutes, not hours
  • Fast tests run first

4Facilitation tips

Follow one real changeA real recent change gives real numbers and stories; a generic walk-through hides the waits.
Count the waitingAsk how long work sits between stages, not just how long each stage runs.
Make it understandableUse plain names for stages, so product owners and managers can follow it too.
One improvement at a timeFix the biggest bottleneck, measure, then move on. The constraint will move.
A red build is everyone's problemAgree that fixing a broken main branch comes before starting new work.
Keep it currentRedraw the map when the pipeline changes, and revisit it every few months.
Common pitfalls: mapping the pipeline as designed, not as it really runs; blaming the people who own a slow stage; trying to fix everything at once; adding gates instead of removing waits; leaving out testing, security or operations.

5After the session

Straight away

Add the chosen improvement to the backlog, with its owner and check date.

Each iteration

Track the number you expect to move.

Monthly

Review deployment frequency and lead time on the Delivery Metrics & Tech Debt board.

Quarterly

Re-map the pipeline, or run the Continuous Delivery Health Check.

6How it fits the toolkit

The delivery engineering tools work as a set. SDLC at a Glance shows where each stage of the lifecycle fits. The Delivery Pipeline Canvas maps how changes reach production, the Test Strategy decides how quality is built in, and Release Readiness & Strategy plans each release. The Continuous Delivery Health Check tracks the practices over time, and Delivery Metrics & Tech Debt measures the results. For the wider flow from idea to customer, use the Value Stream Map.
