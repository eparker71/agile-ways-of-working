# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static site of printable agile facilitation tools: A3 landscape boards and posters (each as `.html` + `.svg`), A4 facilitator guides (each also as `.docx`), three cheat sheets (the main one, Jira and Azure DevOps), and reference pages (role guide, tools by industry, For Project Managers, glossary, good practices, anti-patterns, scenarios, workshop recipes). Nearly everything is generated by Python 3 scripts in `_generator/` (standard library only, no dependencies); there is no test suite beyond `check_site.py`. Published with GitHub Pages (legacy build from `main`, repo root, `.nojekyll`) at https://eparker71.github.io/agile-ways-of-working/. Pushing to `main` deploys.

**Purpose** (also on the About page and in the README): help teams get better at delivering things that matter, without an expert in the room; judgement over compliance. Weigh new additions against it, including whether their effect could ever be seen.

## Commands

```sh
python3 _generator/build_all.py     # run every generator in order; build_meta.py must run last
python3 _generator/check_site.py    # links + anchors, metadata, SVG/Word validity, sitemap, PDFs, cheat sheet overflow, contrast
python3 _generator/build_pdfs.py    # A3 PDFs of every board into pdf/ (needs Chrome); only remakes changed boards
```

`build_pdfs.py` also prints the documents in its `DOCUMENTS` list (the A4 case study `basket-team-story` and its 12-step `basket-team-highlights` edition, both from `build_story()`; the highlights and their lessons are `HIGHLIGHTS` in story.py) from their page's print stylesheet; their fingerprint covers the page and the images on it, so changing a worked example remakes it too.

**After changing any board**, run `build_all.py`, then `build_pdfs.py`, then `build_all.py` again (pages link to a PDF once it exists). PDFs carry timestamps so they aren't rebuilt in CI; `pdf/manifest.json` stores a fingerprint of each board's SVG and `check_site.py` fails if a PDF is missing or stale. `print-pack.html` (built by `build_recipes.py`) lists every PDF, grouped by the home page sections.

Individual generators (all run by `build_all.py`; `build_pdfs.py` is separate): `build_boards.py`, `build_guides.py`, `build_roles.py`, `build_glossary.py`, `build_antipatterns.py`, `build_practices.py`, `build_industries.py`, `build_prompts.py`, `build_picker.py`, `build_pm.py`, `build_scenarios.py`, `build_recipes.py`, `build_meta.py`. CI (`.github/workflows/checks.yml`) runs `build_all.py`, fails if `git diff` shows the committed output is stale, then runs `check_site.py`. So **always run `build_all.py` and commit its output**, and keep generators deterministic: no timestamps, sorted globs (Word files use a fixed zip timestamp and no compression for this reason). **Don't finish by running a single generator:** every generator rewrites its pages without the `<!-- meta -->` block, so running e.g. `build_glossary.py` after `build_meta.py` leaves stale output and fails CI. Re-run `build_all.py` last.

Each script regenerates everything it owns (there's no per-file target). They're idempotent.

**Worked examples & recipes:** `EXAMPLES` in build_boards.py builds `worked-example-<board>.{svg,html}` by reading the blank board and appending a `<g class="worked-example">` layer (Caveat handwriting via `hand()`, stickies via `note()`, `tick()` for checkboxes); placeholders are stripped by `clean()`. Coordinates are hand-placed, so re-screenshot an example after changing its board's layout. A guide links to its worked example if `worked-example-<first board>` exists. `build_recipes.py` reads `_content/recipes.md` (tool titles must match TOOLS) and writes workshop-recipes.html with the example gallery. Gallery entries live in `EXAMPLES` in build_recipes.py (key, title, one-line description) and are grouped by the home page section of their board's card, in home page order; the build stops if a board has no card. `STORY` in `_generator/story.py` puts every worked example on a dated timeline: build_recipes.py turns it into `basket-team-story.html`, and `write_example()` uses its order for the previous / next bar above each example. The build stops if an example is missing from it, so add a dated line there for each new example and keep it consistent with the storyline. `write_example(..., strip=[...])` removes extra placeholder labels an example fills or empties.

**Metadata:** `build_meta.py` inserts a `<!-- meta -->` block after `<title>` in every non-redirect page (description taken from the page itself, Open Graph/Twitter tags, canonical URL, favicon), and writes `sitemap.xml`, `robots.txt` and `404.html` (absolute links, since Pages serves it from any path). Hand-written pages get the block too; don't edit inside it. Regenerate `og-image.png` by screenshotting `_generator/og-card.html` at 1200×630 with headless Chrome.

## Generated vs hand-written

Never edit generated files directly; edit the script and re-run.

- **Generated:** every board and poster except Marginal Gains, `worked-example-*`, every `facilitator-guide-*.{html,docx}` except Marginal Gains, `start-here-by-role.html`, `glossary.html`, `anti-patterns.html`, `good-practices.html`, `tools-by-industry.html`, `prompt-library.html`, `find-a-tool.html`, `for-project-managers.html`, `scenarios.html`, `workshop-recipes.html`, `basket-team-story.html`, `basket-team-highlights.html`, `sitemap.xml`, `robots.txt`, `404.html`.
- **Hand-edited content:** `_content/scenarios.md` and `_content/recipes.md` (formats explained at the top of each). Tool titles in them must match `TOOLS` exactly or the build stops. `.github/ISSUE_TEMPLATE/scenario.yml` is the public suggestion form.
- **Hand-written:** `marginal-gains-workshop-board.{svg,html}`, `facilitator-guide-marginal-gains.html`, `scrum-master-agile-coach-cheat-sheet.html`, `jira-cheat-sheet.html`, `azure-devops-cheat-sheet.html`, `make-it-yours.html`, `about.html`, `index.html`, `LICENSE.md`.
- **Brand:** colours, fonts and the credit line (© author · CC BY 4.0 · site) live in `_generator/brand.py` and are imported by the generators. The hand-written pages carry the same values by hand, so update them too when rebranding. `SITE` (in the credit line) points to the original site; `PUBLISH_AT` is where this copy is published and drives canonical URLs, previews and the sitemap.
- `index.html` is hand-written **except** the regions `build_roles.py` maintains: the `<!-- roles:… -->` / `/* roles:css */` blocks, each card's `data-roles` attribute, each card's `Example` link (added when `worked-example-<board>` exists), and the label of each card's `.svg` link (`SVG_LABEL`, with an `SVG_TIP` tooltip explaining what an SVG is, both in brand.py). Guides use the same label and tooltip for their `.svg` link.
- `build_guides.py` copies its CSS from `facilitator-guide-marginal-gains.html` at run time, so editing that file's `<style>` restyles every guide.
- `jira-cheat-sheet.html` was assembled from the main cheat sheet's CSS, and `azure-devops-cheat-sheet.html` from the Jira sheet; they share styles by copy, not by reference. Both must print to exactly 1 A3 page.

## Architecture

**`build_boards.py`** draws SVG by string-building on a fixed 1680×1190 canvas (A3 at print). Layers:
- Primitives: `T` (text), `R`, `L`, `field` (label + write-on line), `lines`, `checkbox`, `sticky`, `para`.
- Components: `header` (navy band to y≈138; right side takes `legend(...)` or `header_fields([...])`), `panel(x, y, w, h, num, title, color, note)`, `sticky_zone`, `table`, `quad_grid`, `kanban_cols`, `step_cards`, `footer`.
- Colour pairs are `(dark, light)` tuples (`BLUE`, `EMERALD`, `PURPLE`, `ORANGE`, `RED`, `AMBER`, `FOREST`, `SKY`, `SLATE`); `ACCENT` is the orange brand colour.
- Each tool is a `build_<name>()` function ending in `write_board(slug, title, desc, body)`, and is called from `__main__`. Boards are cadence-neutral: one board per tool, with a write-in blank (`strip_blank`) where the period matters. `write_redirects()` turns the old `retro-board-*-{sprint,quarter}.html` and `marginal-gains-workshop-board-{sprint,quarter}.html` names into redirect pages; it overwrites those files, so never reuse those names. Prefer "iteration" to "sprint" except on Scrum-named tools (Sprint Planning, Sprint Review).
- Usual layout: content from y=148 to y=1060, 24px outer margin, 14px gaps; rows often split 808 / 397 / 397 or 1082 / 536 wide.
- `write_board` also adds a phone-only note under the board (`PHONE_CSS`, `phone_note()`; the hand-written Marginal Gains page has a copy) and print CSS that fits the board to one A3 landscape sheet.
- `write_board` adds a fixed "Facilitator guide →" link from `guide_for(slug)`. That function strips `-board`/`-poster` (`retro-board-X-{sprint,quarter}` → `facilitator-guide-retro-X.html`), so a guide's `slug` must match.

**Licensing:** content is CC BY 4.0 and `_generator/` code is MIT (`LICENSE.md`). Every page and board shows the credit line; keep it on new pages.

**`build_guides.py`** holds guide content as dicts (in `GUIDES` and lists appended to it). Required keys: `slug, title, subtitle, tag, boards, lede, intro, glance, before, agenda_heads, agenda, sections_title, sections_intro, sections, tips, pitfalls, after, toolkit, foot`. `render()` turns each one into a fixed page layout, and `render_docx()` writes the matching Word file through `docx_writer.py`, a small zipfile-based WordprocessingML writer (headings, bullets, tables, bold/italic runs from simple HTML). Validate `.docx` output by parsing each XML part and with `textutil -convert txt`. `intro`, `before` and `toolkit` may contain HTML; most other fields are escaped. Shared "how it fits the toolkit" paragraphs are constants such as `LIFECYCLE_TOOLKIT`, `PROJECT_TOOLKIT`, `PROGRAM_TOOLKIT`, `FLOW_TOOLKIT` and `ENG_TOOLKIT`.

**`board_spec.py`** builds each guide's "Recreate it in your whiteboard" AI prompt by parsing the board's SVG: rects with `filter="url(#fc)"` are sections (the white text in their header is the title and note), dashed rects inside a headerless panel are zones (e.g. Sailboat), and boards with no panels fall back to rows grouped by vertical gaps. It merges wrapped lines and list numbers, so short repeated digits (e.g. 1–5 score labels) get read as list numbers: draw them as one `<text>` with `<tspan>`s and an `x` attribute. Text is read in baseline order, so in a row of columns (label · description · quote) give each column's first line the same `y`, or the rows interleave in the prompt. To keep a name with its description when they sit on different baselines (key entries, sticky legends), put both in one `<text>`, joined by `<tspan fill-opacity="0">: </tspan>`, and end each wrapped line's tspan with a space. All-caps mono labels, panel subtitles and header fields get sentence-cased by `_case()`, which keeps mixed-case words (SAFe, OKRs) and anything in `ACRONYMS`; add a new acronym there or it comes out lowercase. If you add a new layout primitive, check its spec with `python3 _generator/board_spec.py <board>.svg`. The Marginal Gains guide's prompt block is pasted in by hand, so regenerate it if that board changes. The prompt section carries `id="whiteboard"`; `index.html` and `make-it-yours.html` link to `facilitator-guide-retro-start-stop-continue.html#whiteboard`, so keep that id.

**`build_roles.py`** holds two tables, which are the single source of truth for the role feature:
- `TOOLS`: key → (title, board, guide, href-prefix for matching index cards).
- `ROLES`: id, name, description, three start-with tools, also-useful tools. A role's filter button shows the part of its name before " / ".

It writes the role page, tags each index card by matching the card's `class="primary"` link against the prefixes, and generates the home page's sticky section menu (from `<h2 id="…">` headings, with short labels in `SHORT`) and search box. One script handles role filtering (`#role=<id>` hash) and search together, hiding empty sections and their menu links.

**Reference page generators** (`build_practices.py`, `build_industries.py`, `build_prompts.py`, `build_pm.py`, `build_picker.py`, `build_glossary.py`, `build_antipatterns.py`) share one pattern: a data table at the top (`PRACTICES`, `INDUSTRIES`, `PROMPTS`, `ARTEFACTS`, `NEEDS`, `TERMS`, `ANTIPATTERNS`), checked with asserts against `TOOLS`, anti-pattern labels, glossary terms or `index.html` sections, then rendered to one page. Edit the table and re-run `build_all.py`; a typo in a tool key stops the build with its name. The Basket story pages come from `build_story()` in build_recipes.py, one template for both editions (`STORY_EDITIONS`).

**Home page structure:** `index.html` is grouped into task-based `<h2 id>` sections (set up the team, decide what to build, break down work, …, facilitate & coach). Reference pages sit in the header's hand-written strip, not as cards, in two rows: "Get started" (Find a tool, role guide, tools by industry, Right-size, the team story, recipes) and "Reference" (glossary, practices, anti-patterns, scenarios, prompts, cheat sheets, About and so on), under a "Find a tool in 3 questions" button. `find-a-tool.html` (build_picker.py) maps `NEEDS` to Scenario Playbook titles and ranks their tools by the role (ROLES) and size (STARTER_KITS); every role × size × need is computed and checked at build time, so renaming a scenario breaks the build. On phones the strip and role bar become single swipeable rows (CSS in `index.html` and `FILTER_CSS`). A new section needs an `id` on its `<h2>` and, ideally, an entry in `SHORT`.

**Adding a tool** touches five places:
1. A `build_*` function, plus its call in `__main__`.
2. A guide dict.
3. A card in the right `<h2>` section of `index.html` (copy a neighbour; leave out `data-roles` and the `Example` link, which `build_roles.py` fills in).
4. Entries in `TOOLS` and `ROLES` in `build_roles.py`, then re-run it.
5. Rows in `README.md`'s tool table and lifecycle sections.

If the tool introduces new terms, add them to `TERMS` in `build_glossary.py`. If it puts a good practice into practice, add its key to that practice in `PRACTICES` (`build_practices.py`, which also maps each practice to the anti-patterns it prevents by their short labels; renaming an anti-pattern's short label breaks the build). If it comes from an idea people search for (such as lean), add it to `TAGS` in `build_roles.py`: hidden keywords on its home card that the search box matches. If it suits particular kinds of work, add it to `INDUSTRIES` in `build_industries.py` (start-with, also-useful or skip lists). Optionally, add it to a scenario or recipe in `_content/`, to `STARTER_KITS` in `build_recipes.py`, to a prompt's tool list in `PROMPTS` (`build_prompts.py`, the Prompt Library) or a row of `ARTEFACTS` (`build_pm.py`, For Project Managers) if it does the job of a familiar project artefact, or to the cheat sheet's "Your Toolkit" panel (then re-check overflow).

**Adding a worked example** touches four places: an `example_<name>()` function registered in `EXAMPLES` (build_boards.py); a gallery line in `EXAMPLES` (build_recipes.py); a dated step in `STORY` (`_generator/story.py`) that fits the Basket team's storyline, or the build stops; then `build_pdfs.py` for its A3 PDF. Add it to `HIGHLIGHTS` only if it's one of the story's key moments. The guide link, gallery card, story pages, previous / next bar and home card's Example link all follow automatically.

## Verifying changes

`check_site.py` covers links and anchors, metadata, SVG/Word validity, the sitemap, and cheat sheet overflow and page counts (the overflow check waits for `document.fonts.ready`, since the fallback font causes false overflows). Everything visual is checked by rendering with headless Chrome (`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`):
- **Screenshot a board:** `--headless=new --hide-scrollbars --window-size=1728,1238 --virtual-time-budget=4000 --screenshot=<png> file://<path>`. Look for text overlapping panel edges, legends or other text. `text_w()` is only a rough width estimate.
- **Page count:** `--print-to-pdf`, then count `/Type /Page` objects. Chrome puts them in compressed object streams, so a plain `grep` finds none: inflate each `stream…endstream` with `zlib` and count there too. Boards should print to exactly 1 A3 landscape page; guides to 3–4 A4 pages; the main cheat sheet to exactly 2 A3 pages; the Jira and Azure DevOps sheets to 1 each.
- **Cheat sheet overflow:** `check_site.py` does this. The main cheat sheet is nearly full. Adding a line to one panel can overflow a different panel in the same grid row, often Team Development on side 2. Rebalancing the `.s2` grid columns has worked better than shrinking text.
- **Phone width:** headless Chrome won't render narrower than 500px, so load pages in a 390px-wide `<iframe>` inside a wider harness page (pass `--allow-file-access-from-files` to measure inside it). The `.tbl` tables scrolling sideways inside their panel on phones is intentional.

## Conventions and gotchas

- **Writing style:** British spelling (prioritisation, visualise, colour). Framework-neutral: don't brand the toolkit with any methodology. Name a framework only as the source of a practice (e.g. "big-room planning (SAFe: PI Planning)"). Credit originators in board taglines and guide intros. Trademarked models carry a notice (ADKAR® → Prosci, Inc.; Cynefin® → Cognitive Edge Pte Ltd; PMI®, PMP®, PMI-ACP®, PMBOK® → Project Management Institute, Inc.) in the board footer tag and guide. Before basing a tool on someone's framework, check its licence: share-alike (CC BY-SA, e.g. Lean Canvas, cynefin.io) or non-commercial (CC BY-NC, e.g. Liberating Structures) text can't be copied into this CC BY 4.0 site, so describe it in our own words and credit it, or design an original alternative (as the Product Bet Canvas did).
- **`÷` glyph:** in Geist / Geist Mono at board sizes it reads as `+`. Use `/` instead.
- **`header_fields` labels:** the write-on line starts 96px after the label start, so keep labels to about 15 characters.
- **`panel(num=...)`:** accepts letters too (the RAID board uses `"R"`, `"A"`, …). Pass `None` for no badge.
- **Contrast (WCAG AA):** `check_site.py` measures text contrast on one page of each kind; keep it passing. Light-background small text uses `#5B6B82` (pages, `--muted`) or `MUTED = "#566578"` (boards), not `#94A3B8`/`#64748B`. On navy, use `#8291A6` or lighter, never `#475569`. White text sits on `#C2410C`, not the brand orange `#eb6c36` (3.1:1); keep the brand orange for bars, borders and accents. Faded board text uses `op=".88"`; only decorative glyphs (›, ↓) and write-over placeholder hints inside zones may be fainter. Board SVGs aren't covered by the automated check.
- **Fonts and libraries:** Instrument Serif, Geist and Geist Mono. Boards' `.html` load them from Google Fonts; standalone `.svg` files `@import` them. The only other external asset is GoatCounter's count script, added to every page's `<!-- meta -->` block by build_meta.py when `GOATCOUNTER` in brand.py is set (empty = off; copies should leave it empty). The 404 page counts as `404/<missing path>`.
- **Feedback:** each guide ends with `feedback_html()` (build_guides.py; the Marginal Gains guide has a copy): "Was this guide useful?" buttons that appear only when GoatCounter has loaded and send a `feedback/<slug>/useful|not-useful` event, plus a link to the `used-it.yml` issue form (`FEEDBACK_URL` in brand.py). Its CSS lives in the Marginal Gains guide's `<style>`, like the rest of the guide styles.
