“Where does work wait, and is that visible on our board?”

Most team boards show “To do, Doing, Done”, which hides where work actually waits. Good board design starts from the team's real workflow, including the queues between steps, then adds WIP limits so the team finishes before starting, and explicit exit policies so everyone knows when an item can move. Classes of service make it clear how urgent and date-driven work is handled. The practices come from the Kanban Method (David J. Anderson) and the Kanban Guide.

1Before the session

  • Print the board at A3 or 11×17, or load the SVG as a digital background
  • Take a photo or export of the current board
  • Pick 3–5 recently finished items to trace through the workflow
  • Bring cycle time and throughput data if you have it
  • Sticky notes and markers; the team's Definition of Done

2Agenda & run-sheet

TimeSectionFacilitator notes
0–20Trace real workWalk recent items from request to done. Write every step and every place they waited.
20–451 · Workflow ColumnsTurn those steps into columns, left to right. Mark each as active work or a queue. Write the exit policy for each.
45–60WIP limitsSet a limit for each in-progress column. A useful start is the number of people who work in it, then lower it over time.
60–802 · Classes of ServiceAgree when each class applies, how it's treated, and how many items of each can be in progress.

3Making each part strong

Quality checks for each part of the design.

1 · Workflow Columns

  • Matches real steps
  • Queues are visible
  • Each has an exit policy

WIP limits

  • Every in-progress column has one
  • Low enough to cause conversations

2 · Classes of Service

  • Expedite is rare and limited
  • Fixed-date work is visible early

3 · Board Policies

  • Pull, don't push
  • Blocked items are obvious
  • Written on the board

4 · Cards & Swimlanes

  • Age is visible on each card
  • Few or no swimlanes

5 · Flow Metrics

  • Two or three, reviewed regularly
  • Used to learn, not to judge

4Facilitation tips

Model what is, not what should beStart with the real workflow, including the awkward parts. Improve it later.
Show the queuesWaiting is usually most of the elapsed time. A “Waiting for review” column makes it visible.
WIP limits are a conversationWhen a column is full, the question is “how can I help finish something?”
Expedite sparinglyIf everything is expedite, nothing is. Limit it to one item at a time.
Make age visibleShow days in progress on each card so ageing work stands out.
Evolve the boardReview the design at retros. Small, regular changes beat a big redesign.
Common pitfalls: columns named after people or teams; no queue columns; WIP limits set so high they never bite; ignoring limits when busy; too many swimlanes; policies that exist only in someone's head.

5After the session

Straight away

Rebuild the physical or digital board to match the design. Write the policies on it.

First week

Walk the board right to left at every daily sync. Notice when limits bite.

Each retro

Ask: is the board still showing reality? Adjust one thing at a time.

After a month

Start the Ageing WIP chart using the cycle time data the board now gives you.

6How it fits the toolkit

The flow pack works as a set. Kanban Board Design makes the workflow visible and limits WIP. Ageing WIP & SLE shows which items are at risk and sets the swarm triggers used in Buffering & Swarming. Blocker Clustering finds why work gets stuck, and the Skills Matrix shows who can swarm. Bring the results to retrospectives and the Team Health Check.

Show the prompt
Create an editable whiteboard for “Kanban Board Design”, a workshop board.

Purpose: Design a board that shows how work really flows: columns, WIP limits, exit policies and classes of service.

Layout: a wide landscape board (about 16:11). Make one frame per section below, placed as described. In each frame, add the section name as a heading, then its content as short text labels or empty fields to fill in. Leave space in each frame for sticky notes. Use the header colour given. Keep the wording as written and don't add extra content.

Header fields to fill in: Team, Date

Sections:
1. Workflow Columns: top full width, about 100% wide and 40% tall; header colour blue.
   Subtitle: Left to right · one column per real state or queue
   Content: Column 1: · e.g. Options · Column 2: · e.g. Ready · Column 3: · e.g. Building · Column 4: · e.g. Waiting for review · Column 5: · e.g. Testing · Column 6: · e.g. Ready to release · Column 7: · Done · Name: (×7) · WIP limit: (×7) · Done when (exit policy): (×7) · Active (×7) · Queue (×7)
2. Classes of Service: middle left, about 65% wide and 35% tall; header colour purple.
   Subtitle: How we treat different kinds of work
   Content: Class: · When to use it: · Our policy: · Limit: · Expedite · Urgent, high cost of delay now · Fixed date · Value drops after a date · Standard · Most work, in priority order · Intangible · Improvement, tech debt
3. Board Policies: middle right, about 35% wide and 35% tall; header colour slate grey.
   Subtitle: Write them on the board
   Content: We pull work when: · Blocked items are marked by: · Replenishment: when & who: · We walk the board at: · Definition of Done lives at: · Policies reviewed every:
4. Cards & Swimlanes: bottom left, about 50% wide and 20% tall; header colour sky blue.
   Content: Each card shows: · Title · Owner · Age (days) · Blocked flag · Class of service · Due date · Swimlanes (if any):
5. Flow Metrics to Watch: bottom right, about 50% wide and 20% tall; header colour dark green.
   Subtitle: Learn, don't judge
   Content: WIP · items in progress · Throughput · items done per week · Cycle time · start to done, in days · Work item age · how long open items have run · Blocked time · days items spend blocked · Flow efficiency · active time / total time

Footer questions: “Where does work wait, and is that visible on our board?” “What would happen if we lowered this WIP limit by one?”
